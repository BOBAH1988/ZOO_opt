# mail-automation — автоматизация рутины: рассылки, документы, закупки и отчёты

## Репозиторий

https://github.com/BOBAH1988/mail-automation (приватный)

## Что делает эта система

Рутина в почте и в закупках съедает часы и даёт ошибки: прайс ушёл не всем,
заказ переслали не туда, цифра в отчёте посчитана не по тем данным. Система
забирает это на себя — без участия человека и без включённого компьютера,
в облаке GitHub Actions.

Польза в трёх вещах:

- **Экономит время.** Регулярные действия — рассылка прайсов, пересылка
  заказов и счетов, ответы по дебиторке — идут сами, по расписанию.
- **Поднимает качество.** Одно и то же письмо уходит всем адресатам и
  одинаково: проценты, адреса, вложения не зависят от того, кто и когда
  нажал кнопку.
- **Убирает случайные ошибки.** Проверки и защиты от повторов не дают
  разослать прайс дважды, отправить счёт не тому клиенту или выпустить
  отчёт, посчитанный по неразобранному файлу.

Проекты добавляются по мере надобности — не только рассылки, но и то, что
помогает в ежедневной работе. Два последних:

- **«Рекомендации к заказу» (проект 13)** — сверяет полный прайс с остатком
  на складе и продажами за три месяца, собирает список того, что заказать.
  Считает сам, а не «на глаз», и показывает только проверяемые цифры.
- **KPI «Продажи» (проект 12)** — раз в день разбирает файл с продажами и
  показывает выполнение плана по направлениям и начисление по мотивации.

**Важное примечание про автоматизацию:** На данный момент все cron-расписания в GitHub Actions отключены (см. изменения workflow). Рассылки и отчеты теперь запускаются **только вручную через PWA-приложение**. Планируется интеграция полноценной автоматизации с расписанием в будущем.

Сейчас реализовано **четырнадцать проектов**, использующих общий код:

### Проект 1: "Лемур" — прайс Прусакова (по пятницам И понедельникам)

_Workflow "Почта пт" (пятница) и "Почта пн-вт" (понедельник), ключ `lemur`,
скрипт `run_pipeline.py`_

Одно и то же действие выполняется дважды в неделю: пн и пт (с августа 2026).
Проверяется в 07:37, 08:07, 08:37, 09:07, 09:37 и 10:07 (МСК) в оба дня.

1. Проверяет почту на письмо от `zookingdom@mail.ru` с темой **"Прайс Прусакова.xls"**
2. Скачивает, конвертирует .xls → .xlsx, раскрашивает (новинки — зелёным, акции — жёлтым)
3. Рассылает клиентам с темой "Доброе утро, Ваш прайс"
4. Если письма нет к 9:30 — напоминание поставщику "Вышлите Прайс Прусакова"
5. Если письма всё ещё нет к 10:00 — уведомление на личный email
6. После успешной отправки — уведомление "Прайс Прусакова отправлен"

### Проект 3: "Сети Ухта" (по понедельникам, отправка в любое время)

_Workflow "Прайс Сети Ухта" (отдельный), ключ `sety`, скрипт `run_pipeline_sety.py`_

Отличается от первых двух: **не ждёт входящего письма** — заранее готовый
файл прайса лежит в репозитории, скрипт просто рассылает его по списку.
Автоответчики получателей ("вне офиса" и т.п.) никак не влияют на работу,
так как скрипт вообще ничего не читает из почты.

- Файл прайса: `scripts/price_files/Прайс Зоо Логистик сетям.xlsx`
  (заменяется вручную через Upload files при изменении цен)
- Получатели — в файле `scripts/recipients_sety_ukhta.txt`
- Тема: "Здравствуйте, прайс от ООО "ЗОО Логистик""
- Текст: "Заказ принимаем до вторника 15-00, минимальный заказ 5000р. Доставка в чт."
- После отправки — уведомление "Прайс сетям выслан"
- **Окна отправки больше нет: первый слот дня отправляет в любое время.**
  Раньше скрипт ждал 09:00–12:00 и раньше тихо выходил. Замер 05.10.2026
  показал, почему это было ошибкой: GitHub из 16 cron-слотов выполнил **два**
  (04:45 и 08:25 МСК), оба попали в «рано» и оба вышли тихо — прайс сетям за
  неделю не ушёл. Ждать следующего слота бессмысленно: его может не быть.
  Поздняя отправка шестнадцати магазинам полезнее, чем тишина. После
  12:00 МСК уведомление приходит с темой «⚠️ Прайс сетям отправлен с
  опозданием» и указанием фактического времени
- **Cron — сетка слотов 02:05–09:35 МСК каждые 30 минут** (16 запусков).
  Задержки Actions в 3–6 часов — реальность (28.09.2026 слот 08:09 исполнился
  в 14:38), но самой сетки мало: выполняет GitHub из неё 1–2 запуска. Сетка
  остаётся по той же причине — чем больше слотов, тем выше шанс, что хотя бы
  один дойдёт
- Есть чекбокс **"Не дублировать рассылку"** (включён по умолчанию): перед
  отправкой скрипт смотрит папку "Отправленные" — если **этот файл** уже
  уходил сегодня (**например, вы отправили его вручную**, а потом
  отработал задержанный слот), второй раз магазинам не уходит. Ищется по
  имени вложения, а не по теме: у проекта 14 тема общая с этим (см. «Защита
  от повторной отправки у проектов 3 и 14»). При **ручном**
  запуске вместо молчания приходит письмо «Прайс сетям повторно не отправлен» —
  иначе нажатая кнопка выглядит как сломанная. Плановому запуску уведомление
  не нужно: оно пришло бы дважды за день. Закреплено сценарием
  `p3_после_ручной_отправки_без_дубля`
- **Ручной запуск** (Run workflow) отправляет всегда: нажали кнопку —
  значит отправить сейчас, в любой момент суток (`MANUAL_RUN`). Так же
  ведёт себя тестовый режим
- В тестовом режиме тема письма получает префикс **"[ТЕСТ] "** — такие
  письма защита от дубля за отправку не считает, а в ящике сразу видно,
  что это пробный прогон

### Проект 4: заказ Прусакова оператору (по понедельникам, 07:00–11:30)

_Workflow "Почта пн-вт", ключ `order`, скрипт `run_pipeline_order.py`_

Пересылает заказ клиента (`zoo2017ukhta@yandex.ru`) оператору (`zookingdom@mail.ru`).

- Ищет непрочитанные письма от клиента, классифицирует тему: manual
  (содержит "ЗАКАЗ АММА" — НЕ заказ, см. ниже), corrected
  ("Откорректированный..."), additional ("ДОП.ЗАКАЗ..." — не обрабатывается
  автоматически, только уведомление для ручной проверки), plain (начинается
  с "заказ", при этом точка в начале или конце темы не мешает — «Заказ.» и
  «. Заказ» считаются тем же заказом), остальное игнорируется
- **"ЗАКАЗ АММА" (например "ЗАКАЗ АММА от 28.09") — не заказ.** Это рабочее
  письмо владельца, он разбирает его вручную. Категория "manual" проверяется
  ПЕРВОЙ, потому что тема начинается со слова "заказ" и без исключения
  попадала бы в обработку как обычный заказ (28.09.2026 файл ушёл оператору).
  Такое письмо проект игнорирует полностью: оператору не отправляется,
  уведомлений нет, и письмо НЕ помечается прочитанным — остаётся в ящике
  непрочитанным для ручной работы. Настоящие заказы в этом же запуске
  пересылаются как обычно
- Если есть corrected — пересылается самое свежее из них, а все plain
  письма того же запуска помечаются прочитанными как более неактуальные
- Если corrected нет и ровно одно plain — пересылается оно; текст письма
  до фразы "с уважением" считается комментарием клиента и присылается вам
  отдельным уведомлением "Коментарий к заказу Прусакова"
- Если plain писем несколько, а corrected нет — ситуация неоднозначная,
  шлётся предупреждение для ручной проверки, автоматика ничего не решает
- Если во вложении нет файла — уведомление "Доп заказ или Заказ без прайса"
- Если ничего подходящего не найдено — уведомление "Заказ от клиента не
  пришёл", но только в окне дедлайна 11:00–11:30 и только если за сегодня
  подходящего письма вообще не было
- Предупреждения о неоднозначных письмах ("ДОП.ЗАКАЗ", несколько заказов
  без корректировки) шлются только на первой проверке дня (07:00–07:30):
  такие письма намеренно остаются непрочитанными, иначе одно и то же
  уведомление приходило бы каждые полчаса всё утро
- После успешной пересылки — уведомление "Прайс Прусакова передан оператору"
- Пересылается без промо-текста/вложений (`include_promo=False`)
- Если среди вложений письма есть файл, чьё имя содержит "акция" (без
  учёта регистра — например, оставшийся промо-файл из письма с прайсом,
  на которое клиент случайно ответил) — оператору он НЕ пересылается.
  Вместо этого уходит вам отдельным письмом с темой "Заказ Прусакова
  акция". Оператору по-прежнему пересылается только сам файл заказа
  (первое не-промо вложение). Правило общее, не привязано к конкретному
  файлу — сработает и на будущие акции с "акция" в имени
- Есть **тестовый режим** — пересылка уходит на `NOTIFY_EMAIL` вместо оператора

### Проект 5: счёт Прусакова клиенту (по средам, 09:00–15:00)

_Workflow "Почта ср", ключ `invoice`, скрипт `run_pipeline_invoice.py`_

- Ищет непрочитанные письма от `zookingdom@mail.ru` с темой ровно "Прусакова"
  или начинающейся с "Прусакова Жанна Евгеньевна ИП Ухта Заводская 3стр1.xls"
- Забирает ВСЕ Excel-вложения из письма и пересылает клиенту
  (`zoo2017ukhta@yandex.ru`) одним письмом с темой
  "Добрый день, Счет от ЗОО Логистик, благодарим за ваш заказ"
- Проверка идёт каждые 30 минут с 09:05 до 15:35 МСК (14 запусков workflow) —
  ранние проверки ждут появления счёта (он приходит не раньше 13:00) и дают
  запас на задержки Actions
- **Автоотправка только с 13:00 до 14:30**: раньше 13:00 счёт от Прусакова не
  приходит, поэтому ранние проверки ничего не отправляют; найденное позже 14:30
  письмо автоматически НЕ отправляется — приходит уведомление "отправьте
  вручную" (защита от дублей с ручной пересылкой), само письмо помечается
  прочитанным
- Скрипт смотрит только **непрочитанные** письма: прочитанный счёт считается
  уже обработанным и повторно не отправляется
- Если к 14:30 подходящего письма так и не было — уведомление
  "Счет Прусакова не выслали" (один раз за день, без дублирования)
- После успешной отправки — уведомление "Счет Прусаковой отправлен"
- Есть **тестовый режим** — счёт уходит на `NOTIFY_EMAIL` вместо клиента

- Ищет непрочитанное письмо от `yuriy.novikov1980@mail.ru` с темой "ДЗ" и

### Проект 12: KPI «Продажи» (личный отчёт, ручной запуск)

_Workflow "KPI Продажи" (отдельный), ключ `kpi`, скрипт `run_pipeline_kpi.py`_

Личный мотивационный отчёт Владимира Соколова (Ухта) по выполнению плана
направлений. Раз в день по будням в 14:05 МСК ищет письмо от
`yuriy.novikov1980@mail.ru` с темой **"Продажи"** и вложением
**«Проекция объема продаж.xlsx»** (приходит 2–3 раза в неделю; если
сегодня нет — тихо завершается, ничего не делает).

- Находит в файле блок менеджера **«Соколов Владимир (Ухта)»** (якорь в
  столбце A, под ним строки направлений) и берёт факт (H) и план (I)
- Сопоставляет направления по алиасам из `KPI_ORDER` (нормализованное
  написание, регистр и пробелы не важны). В файле 8 направлений: Общий,
  Наши наполнители, Корма для кошек и собак, Лакомства + четыре
  спецзадачи. Названия в файле отличаются от мотивации — связь по
  планам и личному листу сентября: «Лемниската» = «Корма Лемисканта»
  (план 10 000), «Деликана» = «Корма ПРОрацион» (план 50 000; в августе
  была доп.мотивом со ставкой 5%). «Прочее» и отсутствующие у менеджера
  направления не выводятся
- Считает по конфигу `kpi_config.py` (сетка мотивации обновляется в нём —
  по таблице октября 2026 ступени основных направлений 80/90/95/100%, Общий
  70/80/100%; компенсации 12 000 ₽, оклад 20 000 ₽):
  **%** — достигнутая нижняя граница ступени (факт 83% → пишет «80%»),
  **Факт %** — достигнутая НИЖНЯЯ граница ступени (факт 83% →
  «80%»; ниже первой границы → «0%»), **>>%** — следующая ступень
  (80% → «90%»; все выбраны — «—»),
  **Осталось** — сумма продаж до следующей ступени (план × следующая
  граница − факт; и ниже первой границы тоже, а не весь план),
  **Начислено** — сумма по достигнутой ступени из KPI_BONUS (ниже первой
  границы → 0, дальше по ступеням до максимума), **Проекция** — ожидаемое
  начисление за месяц: факт в среднем за одну ПРОШЕДШУЮ отгрузку × все
  отгрузки месяца → ступень этого проекционного факта (БЕЗ округления
  вверх: 79% — ступень 70%, а не 80%; 99% — не 100%) → начисление по
  ней; премия за перевыполнение «Общего» тоже считается от проекционного
  факта. На последней отгрузке совпадает с «Начислено», до первой — «—».
  **Пр.%** — проекция ПРОЦЕНТА на конец месяца (тот же проекционный
  факт к плану, без округления до ступени): сколько процентов ожидается
  исходя из текущих темпов продаж; до первой отгрузки — «—».
  Прошедшие отгрузки считаются от ДАТЫ получения письма с отчётом
  (заголовок Date, МСК): сколько четвергов отгрузки наступило до этой
  даты; сам день письма ещё не считается (отчёт приходит ~14:05,
  отгрузка этого дня ещё не закрыта). Данные файла (недельные колонки
  C–G, ячейка B1 с месяцем) в шапке НЕ используются: в исходнике месяц
  могут не обновить — раньше из-за этого в шапке стоял прошлый сентябрь.
  Для «Общего» при ≥100%
  цель 105% от плана (как в оригинале). В HTML-таблице значения по
  центру, названия направлений — слева. **Спецзадачи** (Бест Диннер,
  Зилли, Деликана, Лемниската — в мотивации «Корма ПРОрацион» и
  «Корма Лемисканта») считаются иначе — `KPI_SPECIALS`:
  начисление = ставка × ФАКТ направления (факт > плана → верхняя
  ставка, иначе включая ровно 100% → нижняя)
- Выводит направления, по которым ЕСТЬ данные (прочерки не заполняются);
  шапка одной строкой: «Месяц Отгрузок было N из M Средняя отгрузка: X»;
  **месяц и N считаются от даты получения письма с отчётом**, а не от
  ячейки B1 вложения. Число отгрузок = сколько раз в
  месяце выпадает день отгрузки — **четверг** (4 или 5), а не календарные
  недели
- Письмо с темой **«Выполнение KPI»** идёт ТОЛЬКО получателю из настройки
  — это личные данные. Тело — **multipart/alternative**: основная версия
  HTML с настоящей таблицей с рамками (в Mail.ru plain-таблица из `|`
  разваливается пропорциональным шрифтом), запасная — моноширинная
  plain-таблица. Обработанное входящее помечается прочитанным.
  Уведомление «отчёт отправлен» НЕ шлётся — основное письмо и так
  приходит только Владимиру; остаётся лишь уведомление об ошибке
  обработки файла. Отдельный тестовый режим не нужен: письмо всегда
  уходит только на `NOTIFY_EMAIL`

### Проект 13: рекомендации к заказу по остаткам (по понедельникам)

_Workflow "Рекомендации к заказу (пн)" (отдельный), ключ `residues`, скрипт `run_pipeline_residues.py`_

Единственный проект, который запускает **другой** проект: сама система
рекомендаций лежит в папке `project residues` (пакет `residues`), а оркестратор,
который поднимает её и присылает результат на почту, — здесь,
в `scripts/run_pipeline_residues.py`.

По понедельникам берёт из почты **одно** письмо оператора — с прайсом остатка
Ухты, — сохраняет вложение и запускает сборку отчёта. Отчёт о продажах за
базовый период письмом **не приходит**: он лежит в репозитории и обновляется
вручную примерно раз в месяц.

- **Отдельный workflow, а не общий диспетчер.** В общем окне опроса
  (каждые 30 минут) отчёт на 26 745 позиций пересобирался бы семь раз в день.
  В `run_all.py` помечен `standalone`: в общий опрос не попадает, но виден
  в `--list` и запускается вручную через `--only residues`
- **Cron — сетка слотов 07:05–10:35 МСК (пн), каждые 30 минут.** Раньше
  был один слот в 10:00 — GitHub Actions задерживал его на 3–6 часов, и
  отчёт уходил в 16:00+. Теперь сетка из 8 слотов: первый реально
  отработавший соберёт и отправит отчёт, повторные молчат по защите от дубля
  (маркер на диске + проверка папки «Отправленные»)
- **Письмо с прайсом приходит уже прочитанным** — его открывают в почтовом
  клиенте. Поэтому поиск идёт среди **всех** писем от оператора, а не только
  непрочитанных: иначе проект считал бы ящик пустым и ушёл бы тихо
- **Прайс опознаётся по имени вложения** (`райс` в названии файла), а не берётся
  первым попавшимся. Слово «Ухта» есть и в теме письма с **заказом клиента**,
  и такой выбор однажды подставил в остаток заказ вместо выгрузки: из 2 823
  позиций осталось 27, и в заказ уехало всё подряд
- Берёт **самое свежее** подходящее письмо — последнее по времени. Несколько
  писем за выходные — обычное дело, оператор мог прислать уточнение
- **Повторный отчёт отсекается по дате письма** (`MAX_LETTER_AGE_DAYS = 6`).
  Раньше защитой была отметка «прочитано», но письмо прочитано заранее и
  погасить его нельзя; без проверки даты проект слал бы один и тот же отчёт
  каждую неделю. Старое письмо = уже обработанный остаток → тихий выход
- **Дополнительная защита от дубля в GitHub Actions**: маркер на диске
  не сохраняется между запусками (чистая среда), поэтому дополнительно
  проверяется папка «Отправленные» — если отчёт с темой «рекомендации к
  заказу» уже уходил сегодня, повторная отправка пропускается. Проверка
  работает по подстроке (без учёта регистра), так как полная тема содержит
  дату
- **Письмо не помечается прочитанным** и остаётся в ящике как подтверждение,
  какой остаток уже уходил в заказ
- **Если письма нет или оно старше 6 дней — тихий выход без уведомления.**
  В понедельник утром такое уведомление пришло бы раньше ответа оператора
  и только пугало
- Отчёт — **один файл** со всеми листами на `NOTIFY_EMAIL`. Дополнительные
  адреса — Secret `RESIDUES_CC` (необязательный, через запятую): чтобы слать
  копию руководителю, код менять не нужно
- **Тестовый режим** (чекбокс в интерфейсе GitHub) — отчёт **уходит**, но
  только на `NOTIFY_EMAIL`: копия руководителю из `RESIDUES_CC` не
  добавляется. Так тест выглядит как боевой запуск, но черновик никто чужой
  не видит. Адрес руководителя добавляют в `RESIDUES_CC` уже после теста
- Отсутствие файла продаж в репозитории — **явная ошибка**, а не тихий выход
- Перед боевым запуском workflow прогоняет тесты `project residues`: поломанная
  сверка обнаружится здесь, а не понедельник утром, когда письмо уже в ящике
- **Почта читается узко.** Поиск идёт по окну в `LOOKBACK_DAYS = 21` день и
  скачивает не больше `MAX_LETTERS_TO_FETCH = 10` писем. Без этого проект
  перебирал бы всю переписку с оператором — каждое письмо целиком, с
  вложениями, — и запуск висел бы минутами на почте вместо расчёта
- **Пакеты ставятся лёгко.** Workflow ставит `requirements-residues.txt`
  (3 пакета), а не общий `requirements.txt`: тот тянет `xls2xlsx`, а с ним
  девять тяжёлых зависимостей, которые проекту не нужны — он читает `.xls`
  сам, через `xlrd`
- **Формат вложения определяется по содержимому**, а не по расширению: вложение
  всегда сохраняется как `прайс Ухта.xlsx`, поэтому расширение о формате не
  говорит ничего. Оператор присылает остаток **в .xls каждую неделю** — это
  штатный путь, а не редкий случай: проект сам конвертирует файл в .xlsx
  (xlrd → openpyxl), сохраняя размеры шрифта, по которым парсер отличает
  раздел от товара. Не-Excel отклоняется сразу и внятно
- Ручной запуск: Run workflow или
  `cd scripts && python3 run_all.py --only residues` — обрабатывает письмо
  независимо от времени суток

Сам отчёт, его настройки и состав проекта — в разделе
«Система рекомендаций к заказу» ниже.

### Защита от повторной отправки у проектов 3 и 14 — ПО ИМЕНИ ФАЙЛА

У обоих проектов **тема письма одна и та же** (это один и тот же документ —
прайс ООО «ЗОО Логистик»), а адресаты разные. Поиск по теме их не различает:
отправив клиенту, проект 3 увидел бы «своё» письмо в «Отправленных» и решил
бы, что сетям уже отправлено, — а это ровно та ошибка, из-за которой сети
остались без прайса.

Поэтому дубль ищется **по имени вложения**:

| Проект             | Файл                                               |
| ------------------------ | ------------------------------------------------------ |
| 3 (сети)             | `Прайс Зоо Логистик сетям.xlsx` |
| 14 (ИП Мамедов) | `Сокращенный прайс.xlsx`             |

Письмо с `[ТЕСТ]` в теме за дубли не считается — иначе пробный запуск утром
заблокировал бы боевой. Проверено сценариями
`p3_после_ручной_отправки_без_дубля` и `p14_после_ручной_отправки_без_дубля`.

## Система рекомендаций к заказу (project residues)

Запуск вручную:

```bash
cd "project residues"
python3 -m residues --order
```

Задача — заменить ручное ведение заказа в Excel: менеджер получает отчёт о
том, каких продающихся позиций нет на складе и в каком порядке их заказывать.

Что делает система:

- читает полный прайс (26 745 позиций), отчёт о продажах 1С (из репозитория)
  и прайс остатка (из письма оператора);
- сопоставляет позиции по связке «артикул + название» — артикул в прайсе не
  является идентификатором: 495 кодов встречаются у разных товаров;
- учитывает перевыданные за год артикулы (мягкое сопоставление по названию),
  проверяя цвет и размер, чтобы чужой товар не удержался;
- берёт базу за последние 3 месяца: позиция, молчащая три месяца, заказом
  быть не может — отсутствие на остатке само по себе спроса не доказывает;
- акции отбираются **по продажам, а не по названию**: акция, которая продаётся,
  заказывается наравне с обычным товаром и сама уйдёт из заказа, когда продажи
  прекратятся;
- показывает **факты, а не прогнозы**: объём в штуках из отчёта 1С.
  «Потери» и «прогнозы» из отчёта убраны — они опирались на предположение, что
  товар отсутствовал все три месяца, а истории остатков не существует;
- отчёт — **два листа**: «Сводка» (шесть чисел, топ-10 по штукам) и
  «Нет на остатке» (единая таблица заказа с автофильтром и закреплённой
  шапкой).

На прогоне 05.10.2026: обработано 26 745 позиций прайса, 4 037 продавались
за 3 месяца, из них **1 821 отсутствует на остатке** — это и есть заказ
(32 722 шт за период).

Настройка одна — `data/order.yaml`: `min_period_sales` (порог отсечения
в штуках) и `min_similarity` (порог сходства названий). Меняется без правки
кода.

Отчёт о продажах обновляется вручную: **Upload files** →
`project residues/Весь ассортимент за 3 мес.xlsx`, примерно раз в месяц.
Без него workflow упадёт с явной ошибкой — молча пропускать нельзя, иначе
неделя заказа потеряется без сигнала.

**Пока новый месяц не подгружен, система считает по последнему файлу** — сколь
бы старым он ни был. Устаревание не поломка и не повод останавливаться.

Чтобы это было заметно, а не тихо:

- на сводке появляется строка `Продажи по 09.2026 (N дн. назад)`; если с
  конца месяца прошло больше `STALE_SALES_AFTER_DAYS = 40` дней, к ней
  добавляется пометка «нужны свежие данные»;
- при этой пометке в тело письма с отчётом добавляется строка
  «Подгрузите свежие данные за прошедший месяц.». В остальных случаях тело
  письма пустое, как и просили.

Порог в 40 дней — это месяц плюс 10 дней запаса: напоминание приходит
заранее, но не мешает, если выгрузка задерживается на неделю. Месяц берётся
из заголовков колонок отчёта 1С («Сентябрь 2026 г.»), потому что в шапке
выгрузки «за 3 мес» период не указан.

Тесты: 166 (`python3 -m pytest tests` в папке проекта), реальные файлы не
нужны — мини-прайсы собираются во временной папке.

## Расписание

**Расписание живёт в одном месте — в таблице `JOBS` в файле

### Параллельный запуск проектов (с августа 2026)

По умолчанию проекты запускаются **параллельно** (до 4 одновременно), что
ускоряет общее время обработки в 3–5 раз. Например, 5 проектов × 2 минуты
каждый = 10 минут (последовательно) → 2–3 минуты (параллельно).

Используется `concurrent.futures.ThreadPoolExecutor` с максимальным количеством
рабочих потоков 4, оптимально для I/O-интенсивных операций (IMAP, SMTP,
обработка файлов). Сбой одного проекта не влияет на остальные — изоляция
ошибок сохранена.

Команды:

```
cd scripts && python3 run_all.py                 # параллельный запуск (по умолчанию)
cd scripts && python3 run_all.py --sequential    # классический последовательный запуск
```

Посмотреть текущее расписание можно командой:

```
cd scripts && python3 run_all.py --list
```

### Задержки GitHub Actions и ранние утренние слоты (сентябрь 2026)

GitHub Actions стабильно задерживает плановые (schedule) запуски на
**3–5 часов** (затор планировщика облака): запуск в 07:05 исполнялся в
11–12 часов, когда утренние окна уже закрыты, и проекты пропускались —
приходилось запускать вручную. По логам это видно точно: KPI 14:05
исполнялся в 17:56–18:02, "Почта ср" приходила в 18:15.

Компенсация: утренние cron-слоты workflow "Почта пн-вт", "Почта пт" и
"Почта ср" сдвинуты на 3 часа раньше необходимого — **каждые 30 минут с 04:05
до 08:35 МСК**. Даже при задержке 3–4 часа исполнение попадает в утренние
окна. Дневные слоты (12:05–17:05, счета клиентам и платёжки) не менялись.

05.10.2026 — "Почта ср" также получила ранние слоты. Раньше её первый
запуск был в 09:05 МСК: с задержкой 5 часов он исполнялся в 14:05 — и
счёт Прусакова попадал под 14:30 cutoff (автоотправка отключалась,
письмо помечалось прочитанным, приходило "отправьте вручную"). С
ранними слотами 04:05 МСК даже при 5-часовой задержке запуск
исполняется в 09:05 — в окно автоотправки.

Это лучшая возможная компенсация без платного хостинга: жёсткой гарантии
от GitHub всё равно нет. Если затор станет 5+ часов, запуск снова может
опоздать — проверить легко через разбор логов (ниже).

**06.10.2026 — пробел 08:35–12:05 в cron «Почта пн-вт» и «Почта пт».**
Ранние слоты заканчивались в 08:35 МСК, а ежечасные начинались в 12:05.
В промежутке 3,5 часы ни один слот не срабатывал: дедлайны Ухты (10:00–
10:30), Дебиторки (11:00–11:30), Лемура (10:00–10:30 в пт) попадали
только при задержке Actions 2–3 часов. Без задержек они пропускались
полностью. Исправлено: утренние слоты продлены до 11:35 МСК
(каждые 30 минут, 16 слотов на каждый день вместо 10). Нагрузка выросла
с 16 до 22 запусков/день — компенсируется за счёт уверенности в
дедлайнах.

**Проект 3 (Сети) — почему у него сетка слотов, а не один.** 28.09.2026
единственный слот 08:09 исполнился в 14:38: задержка 6,5 часа, и прайс
сетям ушёл после обеда вместо утра. У остальных проектов такой риск
снижен заранее — у них много слотов и проверка окна времени, а у проекта 3
отправка безусловная (нет входящего письма, ждать нечего). Исправлено
28.09.2026 в два слоя:

1. **Сетка слотов 02:05–09:35 МСК** (каждые 30 минут, 16 запусков) вместо
   одного — чем больше слотов, тем выше шанс, что хотя бы один дойдёт.
2. **Поздняя отправка вместо тихого выхода.** После 12:00 письмо сетям всё
   равно уходит, но с уведомлением «⚠️ … с опозданием», чтобы опоздание
   было видно сразу, а не пряталось под обычным «Прайс сетям выслан».

**ДОПОЛНЕНИЕ 05.10.2026 (15:34) — ЗАЩИТА ОТ ДУБЛЯ ПРОМОЛЧАЛА.**
В тот день прайс ушёл сетям в 13:34 вручную, а задержанный слот в 15:34
отправил его **второй раз**. Проверка «не найдено» вернула `False` **молча**:
в логе не осталось ни слова, почему она не сработала, и разбираться пришлось
по одному только «письмо пришло в 15:34».

Исправлено в трёх слоях:

- **Проверка обязана говорить.** Теперь она пишет в журнал, какую папку
  открыла, сколько писем просмотрела и какие вложения в них были. Молчащий
  отказ опаснее отсутствия защиты: он выглядит как «дубля не было».
- **Имена вложений читаются мягче.** Раньше имя бралось из `get_attachments()`,
  который отбрасывает части письма без пометки `attachment` и пропускает
  `inline`. Для проверки дубля это опасно: вложение есть, а имя не нашлось.
  Теперь берётся любое имя файла из частей письма.
- **У проекта 3 две независимые проверки** — по имени файла и, если не
  сработало, по теме. Тема для проекта 3 безопасна как запасной рубеж:
  проект 14 отправляет письмо вторым шагом и к этому моменту ещё ничего не
  отправил, поэтому ложного срабатывания не будет. У проекта 14 тема
  остаётся запрещённой — там она общая с третьим.

Закреплено сценарием `p3_дубль_вложение_не_прочитано`: в «Отправленных»
лежит письмо с другим именем файла, и рассылка всё равно не уходит.

Общий вывод по инциденту: **тихий отказ проверки хуже, чем её отсутствие** —
отсутствие видно по дубликату в почте, а тишина выглядит как «всё в порядке».
Третий раз подряд молчаливый отказ (тихий выход проекта 13, «код 2» без
причины, молчащая защита дубля) — это уже не случайность, а привычка
писать проверки, которые не объясняют свой отказ.

Побочный эффект: защита от дубля срабатывает молча (только запись в журнал).
При нескольких слотах уведомление «Прайс сетям уже отправлен» пришло бы
дважды за день — письмо «Прайс сетям выслан» и так уже пришло один раз.
Исключение — ручной запуск: там вместо молчания приходит письмо «Прайс
сетям повторно не отправлен», иначе нажатая кнопка выглядит как
сломанная.

Проект 3 (Сети) — единственный вне общего опроса: он рассылает прайс
безусловно, без проверки почты. В общем окне он разослал бы прайс
шестнадцати магазинам столько раз, сколько диспетчер вызвался бы за утро.
В таблице `JOBS` он всё равно
перечислен (с пометкой `standalone`), поэтому виден в `--list` и
запускается вручную через `--only sety` — его собственный workflow так и
делает.

Поведение при отсутствии письма:

- **Прусакова/Ухта (1, 2)**: в 9:30–10:00 — напоминание поставщику,
  в 10:00–10:30 — уведомление на личный email
- **Заказ оператору (4)**: в 11:00–11:30 — уведомление "Заказ от клиента
  не пришёл". Предупреждения о неоднозначных письмах ("ДОП.ЗАКАЗ",
  несколько заказов без корректировки) — только на первой проверке
  в 07:00–07:30
- **Счёт Прусакова (5)**: в 14:30–15:00 — уведомление "Счет Прусакова не выслали"
- **Дебиторка Ухта (10)**: в 11:00–11:30 — напоминание оператору "Вышлите дебеторку Ухта"
- **ДЗ (7), ВЕТА (8), счета клиентам (9), платёжки (11), Велес (6)**:
  ничего не делается, без уведомлений

Каждое такое уведомление отправляется **один раз**: у него есть не только
начало, но и конец окна (ровно 30 минут — как раз один вызов диспетчера).
Без верхней границы уведомление повторялось бы при каждой последующей
проверке до конца дня.

### Скрытый аудит молчаливых отказов (октябрь 2026)

После инцидента с дублём пройден системный поиск мест, где система может
**тихо** решить неправильно. Найдено и исправлено четыре класса:

- **Проект 6: список принимаемых вложений расширен до PDF.** В разделе
  проекта 6 README обещал только Excel, и код ему соответствовал — прямой
  ошибки не было. Риск в другом: формат вложения задаёт отправитель и
  может измениться, а тогда письмо попало бы в тихий пропуск — без
  отправки, уведомления и записи в журнале (см. следующий пункт). Теперь
  фильтр `VELES_EXTENSIONS = (".xls", ".xlsx", ".pdf")` — как у проекта 11,
  закреплёно сценарием `p6_счёт_в_pdf`. На ваших письмах (всегда Excel)
  поведение не изменилось: `.xls`/`.xlsx` обрабатывались и раньше.
- **Письмо без вложений в проекте 6 пропускалось молча** (`logger.debug` +
  `continue`), хотя в остальных пересылочных проектах на это шлётся
  уведомление. Теперь: предупреждение в журнал, письмо «⚠️ Счёт в Велес
  не переслан» со списком тем и код `RESULT_ERROR`. Письмо **намеренно не
  помечается прочитанным** — оно попадёт в следующую проверку.
- **«Ничего не найдено» писалось на уровне `debug`** — а в логах GitHub
  Actions он не виден (там INFO), и провал был неотличим от штатного
  прогона. Ветка `RESULT_RETRY` переведена на `info`/`warning`.
- **Упавший проект заканчивал запуск зелёным.** `ProjectBase.run()` был
  `-> None` и проглатывал `RESULT_ERROR`: диспетчер помечал проект
  успешным, `run_all.py` выходил с кодом 0 — в GitHub Actions горел
  зелёный прогон при упавшей обработке. Теперь `run()` возвращает признак
  успеха, а `run_all` переводит `False` в код возврата 1. Исключение —
  `RESULT_RETRY` («писем пока нет»): почту опрашивают десятки раз в день,
  и красные прогоны от обычного расписания ничего бы не значили.

Проверки: `p6_счёт_в_pdf` на стенде, в `test_dispatcher_run.py` добавлены
`RESULT_ERROR → код 1` и `«писем нет» → код 0`.

Итог аудита: любой отказ теперь либо уходит письмом, либо виден в журнале,
либо помечает запуск красным. Третьего варианта — «просто промолчать» —
больше нет.

### Надёжность (сентябрь 2026)

- **Безопасные ретраи подключения** (`mail_common`): `smtp_send` и `imap_connect`
  повторяют установку соединения до 3 раз при **транзиторных** сетевых

  Содержательные ответы сервера (`SMTPAuthenticationError`, `AUTHENTICATIONFAILED`)
  **не** ретраятся — повтор неверного пароля лишь приблизил бы блокировку.

  Повтор `sendmail` принципиально НЕ делается: при неясном статусе сервера
  он отправил бы письмо клиенту второй раз. Ретраится только установка
  соединения и логин — у них нет побочных эффектов. Поведение фиксирует
  `tests/check_retries.py`, который гоняется в CI.
- **Один SMTP-код**: `send_email.py` больше не держит собственный SMTP-блок —
  `send_file()` отправляет через `mail_common.smtp_send` (с ретраями и логированием).
- **`scripts/constants.py`**: единое место для SMTP, подписи, promo-настроек;

  раньше `mail_common` импортировал подпись из `send_email` (перевёрнутая
  зависимость; циклическая цепочка разорвана: общее вверх, частное вниз.
- **Линт ruff** с фиксами в CI (`ruff check scripts/ tests/`) ловит мёртвые

- **`timeout-minutes: 10` + кэш pip** у всех Actions-джобов: зависший

- **Локаль-независимая дата в IMAP SEARCH**: месяц в `SINCE` всегда

## Проверка изменений (tests/)

В папке `tests/` лежит стенд, который прогоняет все проекты, **не отправляя
ни одного настоящего письма**: IMAP и SMTP подменяются заглушками, сеть не
используется вообще. Перед правкой и после неё запускается один и тот же
набор из 131 сценария, результаты сравниваются — расхождений быть не должно.

```
cd tests
python3 scenarios.py ../scripts до.json     # до правки
python3 scenarios.py ../scripts после.json  # после правки
python3 check_results.py после.json         # упадёт, если какой-то сценарий с ошибкой

# юнит-тесты чистой логики (из корня репозитория, меньше секунды)
python3 -m pytest tests -q
```

Юнит-тесты (`tests/test_kpi_processors.py`, `test_mail_common.py`,
`test_project_base.py` — всего 48) проверяют чистые функции: расчёт
ступеней/начислений KPI, разбор xlsx, нормализацию тем, границы окон,
ретраи — без стенда и без почты: быстрая обратная связь при правке
логики. Стенд сценариев остаётся главным гарантом интеграции.
Покрытие (`--cov`) печатается в лог CI и сохраняется артефактом
`coverage.xml`.

Подробности — в `tests/README.md`.

### Автопрогон стенда в Actions

Workflow **«Тесты (стенд)»** (`tests.yml`) при каждом push в main сам гоняет
весь набор по порядку: линт `ruff`, юнит-тесты `pytest`, сценарии всех
проектов, расписание диспетчера, диспетчер вживую,
обработку прайсов и проверку ретраев подключений (`tests/check_retries.py`).
Секретов почти не требует и писем не отправляет.
Результат — на вкладке Actions: красный крест = стенд поймал поломку,
чинить нужно до планового дня рассылки. Запустить вручную можно там же:
Run workflow → «Тесты (стенд)».

Нюанс для локальных прогонов: `scenarios.py` внутри делает chdir в папку
`scripts/`, поэтому json-файл результатов создаётся рядом со scripts/
(передавайте путь `../scripts/result.json`, как в tests.yml).

### Диагностика секретов во всех workflow

Во всех четырёх рабочих workflow («Почта пн-вт», «Почта ср», «Почта пт»,
«Прайс Сети Ухта») перед запуском проектов выполняется шаг
**Check secrets format** (`scripts/check_secrets.py`): печатает в лог
диагностику формы `MAILRU_LOGIN` / `MAILRU_APP_PASSWORD` (длина, пробелы,
«@», типичный формат пароля приложения mail.ru), не раскрывая сами значения.
Шаг чисто информационный — на его вывод смотрят, когда почтовые скрипты
вдруг начали падать с AUTHENTICATIONFAILED.

## Известные проблемы

**Задержка автозапуска по расписанию.** GitHub Actions может запускать
scheduled-workflow с опозданием (иногда на час и больше) в периоды
высокой нагрузки — особенно если несколько расписаний в репозитории
попадают в одно и то же время (например, все на ровный час/получас).
Обнаружено на практике 10.08.2026: несколько проектов, у которых
расписание было плотно сгруппировано в окне пн 8:00–11:00, реально
запустились с опозданием до 1.5 часов, а у "Счетов клиентам по списку"
(9 запусков в день) часть срабатываний вообще пропала.
Исправлено в три шага:

*11.08.2026* — время каждого workflow сдвинуто на свои "некруглые"
минуты, чтобы не попадать в момент пиковой нагрузки GitHub (пик —
начало каждого часа/получаса).

*17.08.2026* — главная причина устранена: одиннадцать отдельных
workflow заменены на пять. Девять проектов теперь запускает один
диспетчер `scripts/run_all.py` в общей виртуальной машине. Запусков
в неделю стало 52 вместо 85, а в понедельник утром — 18 вместо 41.
Чем меньше запусков, тем меньше шансов попасть в очередь.

*31.08.2026* — добавлен параллельный запуск проектов. Диспетчер теперь
запускает до 4 проектов одновременно (вместо последовательного выполнения),
что ускоряет обработку в 3–5 раз. Используется `concurrent.futures.ThreadPoolExecutor`.
Меньше времени на обработку = ещё меньше вероятность пиковых нагрузок и очередей
в GitHub Actions. Флаг `--sequential` оставлен для обратной совместимости.

**Почему проект 3 не в диспетчере.** Он рассылает прайс сетям
безусловно, без проверки почты. В общем окне опроса он разослал бы прайс
шестнадцати магазинам столько раз, сколько диспетчер вызвался бы за утро.
Отдельный workflow с проверкой окна отправки в самом проекте такое
исключает.

Именно из-за того, что окно проверял сам проект, а не диспетчер, задержка
Actions осталась незамеченной: единственный слот 08:09 исполнился в 14:38,
и прайс ушёл после обеда. Сейчас у проекта сетка слотов и отправка в любое
время без окна — см. «Задержки GitHub Actions и ранние утренние слоты».

*Проект 4 (заказ оператору) раньше тоже был отдельным по той же
причине. 17.08.2026 ему добавили окно опроса и однократные уведомления,
после чего он переехал в диспетчер. Попутно исправилась давняя
особенность: раньше он проверял почту РОВНО ОДИН раз в 07:04, и заказ,
присланный хоть немного позже, терялся до следующей недели. Теперь
проверяет всё утро.*

**Одновременные запуски.** У всех workflow задан общий
`concurrency: mail-automation` — GitHub выстраивает их в очередь по
одному. Без этого ручной запуск мог наложиться на плановый: оба процесса
прочитали бы одно непрочитанное письмо раньше, чем кто-то пометил его
прочитанным, и получатель получил бы дубль.

**Запуск вне GitHub Actions.** Если cron в GitHub Actions пропускает
слоты (см. выше), а письмо с прайсом пришло — используйте
`scripts/trigger_ukhta.py`: он триггерит workflow `weekly_mon_tue.yml`
через GitHub API каждые 30 минут в окне 07:00–10:30 МСК по пн/вт,
обходя планировщик GitHub. Настройка:

1. Получите PAT с scope `workflow` (GitHub → Settings → Developer settings
   → Personal access tokens).
2. `export GH_TOKEN=your_token_here`
3. Добавьте в crontab (`crontab -e`):

```
# Ухта: каждые 30 мин в 7:00–10:30 по Пн и Вт (МСК)
0,30 7-10 * * 1,2  /usr/bin/python3 /путь/scripts/trigger_ukhta.py
```

Concurrency `mail-automation` предотвращает дубли: если запущенный
процесс ещё работает, новый слот не стартует.

**Битые заголовки вложений.** Некоторые почтовые программы шлют
кириллические имена файлов так, что заголовок `Content-Disposition`
становится нераспознаваемым. Раньше такое вложение терялось и приходило
"не найдено Excel-вложений". Теперь часть письма считается вложением и
по одному наличию имени файла, а сами мы формируем заголовок правильно
(`add_header` вместо присваивания строки).

## Тестовый режим

У трёх workflow диспетчера (пн-вт, ср, пт) и у workflow "Прайс Сети
Ухта" при ручном запуске (Run workflow) есть поля:

| Поле                                                                                             | Что делает                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Тестовый режим**                                                                | всё уходит только на`NOTIFY_EMAIL`, реальные получатели игнорируются. **Выключен по умолчанию**                                                         |
| **Не дублировать рассылку** (только "Прайс Сети Ухта") | пропустить отправку, если прайс с этой темой уже уходил сегодня — вручную или по расписанию. Включён по умолчанию                   |
| **only**                                                                                       | запустить один проект по ключу. Пусто — вся группа                                                                                                                                       |
| **ignore_window**                                                                              | не смотреть на текущее время и день недели. Включено по умолчанию, иначе вручную проект удастся запустить только в его окно |

У workflow проекта 13 ("Рекомендации к заказу") есть только чекбокс
**Тестовый режим**, и он работает не так, как у остальных: письмо с отчётом
**уходит**, но только на ваш `NOTIFY_EMAIL` — копия руководителю из
`RESIDUES_CC` не добавляется. Раньше тест не отправлял ничего вовсе и
оставлял отчёт артефактом; теперь видно ровно то письмо и тот файл, которые
потом уйдут всем, а чужой получатель черновик не видит.

Адрес руководителя добавляют в `RESIDUES_CC` уже после того, как тест прошёл:
Settings → Secrets and variables → Actions → `RESIDUES_CC`.

Письмо с прайсом проект **не гасит** — ни в тестовом, ни в боевом режиме:
оно приходит уже прочитанным и остаётся в ящике как подтверждение, какой
остаток уже уходил в заказ.

> **Внимание: тестовый режим выключен по умолчанию.** Ручной запуск без
> галочки отправляет письма **реальным клиентам**, как плановый запуск по
> расписанию. Если хотите только посмотреть — поставьте галочку
> "Тестовый режим" перед Run.

**Поле `only` работает для любого проекта, даже из другой группы.**
Из workflow "Почта пн-вт" можно запустить `lemur` или `sety`, хотя по
расписанию они там не появляются. Сделано намеренно: так любой проект
проверяется из любого workflow, не дожидаясь его дня и часа. Указанный
в `only` проект запускается независимо от времени, дня и группы —
поле `ignore_window` при этом уже не важно.

Ключи проектов: `order`, `ukhta`, `veta`, `debt_ukhta`, `clients`,
`payments`, `invoice`, `veles`, `lemur`, `dz`, `sety`, `kpi`, `residues`,

Актуальный список всегда можно получить командой `python3 run_all.py --list`

## Как работает защита от дубля (проекты 3 и 14)

Скрипт подключается к ящику по IMAP, находит папку "Отправленные"
(имя папки раскодируется из модифицированного UTF-7, у mail.ru она
называется "Отправленные") и ищет среди сегодняшних писем **вложение с
нужным именем файла**. Нашло — значит, этот файл уже уходил сегодня
(вручную или по расписанию), повторно не отправляем.

Почему не по теме: у проектов 3 и 14 тема одна и та же — «Здравствуйте,
прайс от ООО "ЗОО Логистик"». Это буквально один и тот же документ, просто
адресата разного. Поиск по теме не различил бы их: отправив клиенту,
проект 3 увидел бы «своё» письмо и решил бы, что сетям уже отправлено.
Имя файла различает однозначно: «Прайс Зоо Логистик сетям.xlsx» против
«Сокращенный прайс.xlsx».

- Работает в любом режиме, кроме тестового (тест всегда отправляет), и
  только при включённом чекбоксе "Не дублировать рассылку". Для плановых
  запусков чекбокс включается автоматически
- **Плановый запуск при пропуске молчит** (только запись в журнал): слотов
  в день несколько, и уведомление «уже отправлено» пришло бы дважды
- **Ручной запуск при пропуске пишет вам письмо** «Прайс сетям повторно не
  отправлен» с подсказкой снять чекбокс. Молчать нельзя: человек нажал
  кнопку и должен понимать, почему писем магазинам нет
- Если папку найти не удалось или проверка упала — рассылка всё равно
  уйдёт: проверка не должна приводить к потере прайса (в худшем случае
  уйдёт дубль, о чём придёт уведомление)
- В "Отправленных" проверяются только заголовки писем за сегодня —
  тела и вложения не скачиваются

## Ручной тест

Actions → нужный workflow → Run workflow → **поставить галочку
"Тестовый режим"** → при желании указать один проект в поле **only** → Run.

Чтобы проверить один проект (например, ВЕТА): выбрать "Почта пн-вт",
в поле **only** написать `veta`, галочку "Тестовый режим" поставить.
Письмо придёт вам, реальный получатель его не увидит.

Чтобы проверить сразу всю группу — оставить **only** пустым.

Запуск без галочки "Тестовый режим" — это **боевой** прогон: письма
уйдут клиентам, как по расписанию. Именно так проверяется "Сети Ухта"
с защитой от дубля: утром тестовым прогоном убеждаетесь, что файл и
список получателей в порядке, а плановый запуск в 08:09 разошлёт прайс
магазинам — повторно или вместо вашего ручного запуска.

## История отладки (на случай похожих проблем в будущем)

1. **AUTHENTICATIONFAILED при верном пароле** — опечатка в Secret `MAILRU_LOGIN`;
   помогла проверка через `curl -v --url 'imaps://...' --user 'login:password'`
2. **openpyxl не читает .xls** — нужна библиотека `xls2xlsx`
3. **Чекбокс workflow_dispatch не работал** — контекст `inputs.*` вёл себя
   нестабильно, помог классический `github.event.inputs.*`
4. **Ширина столбцов/перенос текста после конвертации .xls** — не наследуется
   корректно, нужно задавать явно и отключать wrap_text
5. **Markdown "съедает" двойные подчёркивания** — при передаче кода через
   markdown, `__name__` и подобное может визуально терять подчёркивания
6. **.gitkeep случайно попадал в рассылку** — фильтр `_get_promo_attachments()`
   теперь игнорирует файлы, начинающиеся с точки
7. **Уведомления "❌ Ошибка" не доходили** — `notify_error()` вызывал
   несуществующую функцию `send_mail`, а ветка `RESULT_ERROR` в ProjectBase
   вообще не отправляла письмо (только писала в журнал). Теперь сбой обработки
   всегда приходит на `NOTIFY_EMAIL` письмом "❌ Ошибка: <проект>", и это
   покрыто стендовыми сценариями `p0_smtp_сбой_уведомление_об_ошибке`,
   `p0_process_падает_на_этапе_вложения`, `p0_process_падает_после_отправки`,
   `p0_find_messages_новые_первыми`
8. **«Наивные» ретраи чуть не задушили аккаунт** — добавляя ретраи
   подключения, легко написать `except OSError`. Но `smtplib.SMTPException` —
   подкласс `OSError`: неверный пароль (`SMTPAuthenticationError`) стал
   бы ретраиться трижды, приближая блокировку mail.ru. Пришлось
   классифицировать ошибки явно: ретраятся только транзиторные сетевые сбои
   (socket.timeout, ConnectionReset, SMTPServerDisconnected, IMAP4.abort),
   а содержательные ответы сервера (`AUTHENTICATIONFAILED`, неверный пароль) —
   нет. Закреплено проверкой `tests/check_retries.py`, которая гоняется и в CI.
9. **Стенд не ловил баги в аварийном канале** — ветка «исключение в `process()`»
   не была покрыта сценариями, и потому баг с несуществующей `send_mail` прожил
   несколько релизов незамеченным. Теперь хелпер `tests/harness.run_snippet()` +
   сценарии `p0_*` гоняют именно эту ветку, включая проверку, что письмо
   "❌ Ошибка" реально уходит.
10. **Отчёт по ДЗ пришёл нечитаемым** («Áàæóêîâà Àííà Âëàäèìèðîâíà…»).
    Это байты windows-1251, прочитанные как latin-1/cp1252: `Áàæóêîâà` —
    «Бажукова», `¹` — «№». У письма терялась кодировка по дороге (пересылка,
    веб-морда, мобильный клиент, 1С), причём отчёт уходил
    `multipart/alternative` **только с HTML-частью** — без `text/plain` и без
    `<meta charset>`: клиенту, который HTML не показал или перекодировал,
    показывать было нечего. Теперь отчёт идёт двумя частями (текст + HTML),
    в HTML-документ добавлен `<meta charset="utf-8">`, а кодировка всех
    текстовых частей задаётся явно — `MIMEText(..., "utf-8")` в
    `mail_common.py` вместо автоопределения. Закреплено сценарием стенда
    `p0_отчёт_по_дз_читаемая_кодировка`: он проверяет, что письмо 7-битное
    (base64), обе части в utf-8, `<meta charset>` на месте и в тексте нет
    следов mojibake. На старом коде сценарий падает с «в отчёте нет текстовой
    части».

   *Продолжение (28.09.2026, 09:00).* Правка попала в бот, отчёт в 09:02
   отправлен уже новым кодом — а мусор в теле письма остался. Стало
   ясно, что дело не в том, как письмо собирается: `smtp_send` пишет в лог
   «только 7-битные: True», обе части в `base64; charset=utf-8`, а мусор
   «Áàæóêîâà» — это сырые байты windows-1251, которых в письме быть не
   может. Значит, текст перекодирует уже получатель. Поэтому: (а) в
   `mail_common.log_message_structure()` добавлен разбор уходящего письма —
   по логу сразу видно, чей дефект; (б) отчёт теперь **кладут вложением**
   `Otech_DZ.xlsx` как страховка — **вложение убрано 28.09.2026 по просьбе
   владельца, лишний файл в письме не нужен**; (в) `_mime_subtype()` угадывает
   тип вложения по расширению, а не ставит всем `application/octet-stream`
   (это осталось в силе для прайсов и счетов).

   *Настоящая причина (28.09.2026, 10:50).* Обе почтовые правки были лишними:
   письмо уходило корректным base64+utf-8, а мусор был **внутри** текста, ещё
   до упаковки в письмо. Доказательство: «ОПД № 21259 от 10.09.26».encode("cp1251")
   .decode("latin-1") даёт ровно «ÎÏÄ ¹ 21259 îò 10.09.26» из письма, а
   «Реализация Л-00013271 (04.07.19)» → «Ðååëèçàöèÿ Ë-00013271 (04.07.19)».
   Корень: `xlrd` у .xls **без записи CODEPAGE** берёт iso-8859-1 (в его
   `book.py` так и написано: "No CODEPAGE record, no encoding_override: will
   use 'iso-8859-1'"), а выгрузки из 1С идут именно такие.

   Исправление — `mail_common.open_xls_workbook()`: книга читается как есть,
   и если кириллицы нет нигде, а битые латинские символы есть — она
   перечитывается с `encoding_override="cp1251"`. Перечитывание применяется
   только если после него действительно появилась кириллица, так что
   латинские файлы не пострадают. Подключено в проектах 7 и 10
   (`run_pipeline_debt.py`, `run_pipeline_debt_ukhta.py`) и в
   `convert_xls.py` — там та же дыра, потому что `xls2xlsx` внутри тоже
   зовёт `xlrd.open_workbook` без `encoding_override`, то есть **названия в
   прайсах 1, 2 и 3 могли приходить такими же**. Проверено стендом
   `p0_xls_из_1с_без_codepage`: на старом коде падает с «имя с мусором:
   'Áàæóêîâà…'», на новом — проходит.

12. **Проект 13 падал с «завершился с кодом 2», не называв причину.** Код 2
    у проекта «Остатки» означает «ошибка чтения входного файла», и в
    уведомление уходил только код — ни какого файла, ни почему. Настоящая
    причина была вложением из письма: оператор прислал **старый .xls** (OLE2),
    а `save_attachment()` всегда сохранял его под именем «прайс Ухта.xlsx».
    Проверка формата стояла на `target.suffix` — то есть **не срабатывала
    никогда**, имя задавалось вызывающим кодом. Дальше проект открывал
    OLE2-файл через openpyxl и падал.

   Исправлено в двух местах:

* формат определяется по **содержимому** (`detect_excel_format`): ZIP —
  .xlsx, OLE2 — .xls, не-Excel отклоняется сразу и внятно;
* stderr проекта теперь вкладывается в текст ошибки, а не уходит только в
  лог Actions: иначе в почту приходит «код 2», по которому ничего не
  понять.

   **Продолжение.** Оказалось, оператор присылает прайс **в .xls каждую
   неделю** — то есть старый формат это штатный путь, а не редкий случай.
   Первой правки (внятная ошибка «попросите оператора присылать .xlsx») было
   мало: она честно объясняла проблему, но не решала её, а просить оператора
   менять выгрузку — значит сломать заказ и ждать чужую милость.

   Сделан собственный конвертер `scripts/xls_fonts.py`: xlrd читает .xls,
   openpyxl пишет .xlsx, обе библиотеки уже стоят. Он переносит значения и
   **размеры шрифта** — ровно то, по чему парсер отличает раздел (11.0) от
   товара (8.0). Цвет переносить не нужно: проект берёт цвет товара из названия
   и артикула, а не из заливки ячейки. Пакет xls2xlsx при этом не нужен,
   поэтому девять тяжёлых зависимостей в сборку проекта 13 не возвращаются.

   Проверено на настоящем .xls, собранном xlwt: размеры 11/10/8 и значения
   выживают в обоих случаях — когда «тело» прайса 11 пт (стиль пишется только
   в отличающиеся клетки) и когда оно другое (тогда стиль пишется всем).
   Образец лежит в `tests/fixtures/priys-obrazets.xls`, сценарии —
   `p13_xls_конвертируется_с_размерами` и `p13_конвертация_без_xls2xlsx`.

   Закреплено сценариями `p13_формат_вложения_по_содержимому` (формат по
   сигнатуре, .xls уходит в конвертер, PDF отклоняется) и
   `p13_перебор_почты_ограничен`.

   Общая мысль: **ошибка, которая не называет причину, почти равна
   отсутствию ошибки.** Молчаливый выход уже стоил недели заказа (проект 13
   ждал несуществующее письмо), и молчаливое «код 2» — тот же класс проблем.
   А объяснение проблемы без её решения — половина решения: понятная ошибка
   «попросите оператора» показала, где чинить, но чинить было нечего.

13. **Отчёт объявил отсутствующими ВСЕ позиции заказа.** В сводке было
    «Продавались в периоде — база 4 037 поз.» и «из них отсутствуют на
    остатке 4 037 поз.»: не нашлось ни одной. Владелец заметил это по
    наполнителям «Пушистик», которые он видит на складе.

   Первой версией причины назвали конвертер .xls из предыдущей правки:
   якобы xlrd не отдал оформление, клетки получили размер openpyxl по
   умолчанию 11.0, а парсер считает 11.0 РАЗДЕЛОМ. **Это оказалось неверно**
   — такая защита есть, и на присланном после коммита отчёте она не сработала,
   то есть оформление читалось исправно.

   **Первая версия причины («не тот лист») оказалась неверной.** Причина
   нашлась в логе Actions, а не в данных: проект вообще открывал не тот файл.

```
   Остаток: «Панкова Ольга Андреевна ИП Ухта Ленина 24 амма.xls, …»
   На остатке: 27 позиций
```

   Фильтр письма искал тему по слову «Ухта» — а это слово есть и в заказе
   клиента. В остаток попал **заказ Панковой**, а не выгрузка остатка: из
   2 823 позиций осталось 27, и сверка объявила отсутствующими все 4 037.

   Раньше это не проявлялось: проект искал ещё и письмо с продажами, не
   находил его и выходил тихо. Как только продажи взяли из репозитория,
   остался один фильтр — слишком широкий.

   Исправлено в трёх слоях:

* **выбор вложения** — прайс опознаётся по имени файла (`райс` в имени),
  а не берётся первым попавшимся. Письмо с заказом теперь отклоняется;
* **парсер** — по-прежнему берёт лист, где есть названия товаров;
* **конвертер** — падает, если не прочитал размеры шрифта;
* **проект** — не собирает отчёт при нуле товаров в остатке.

   Итоговые правки:

* **парсер** (`residues/pricelist.py`) берёт первый лист, где есть хоть
  одна строка с названием товара, а не `worksheets[0]`;
* **конвертер** по-прежнему падает, если не прочитал размеры шрифта;
* **проект** отказывается собирать отчёт при нуле товаров в остатке — без
  оговорки «но при наличии разделов», как было в первой попытке. Именно
  эта оговорка и пропустила аварию: разделы тоже оказались пусты.

   Хуже всего, что отчёт ушёл: зелёный запуск, письмо на почте, таблица
   «Нет на остатке» на весь ассортимент. По такому отчёту заказали бы всё.

   Исправлено в двух слоях:

* **конвертер** (`scripts/xls_fonts.py`) останавливается с ошибкой, если
  не прочитал ни одного размера шрифта, и не создаёт файл;
* **проект** (`residues/cli.py`) отказывается собирать отчёт, если в
  остатке есть разделы, но нет ни одного товара. Условие именно такое,
  а не «пусто вовсе»: склад может быть законно пуст, а вот «прочитано
  N разделов и ни одного товара» — это провал разбора.

   Тест `test_stock_without_products_is_refused` в проекте и сценарий
   `p13_конвертер_видит_потерю_шрифтов` в стенде закрывают оба слоя.

   Отдельно исправлена тестовая фикстура доставки: её «остаток» состоял из
   одного заголовка раздела без товаров, то есть был нечитаемым, и проходил
   как пустой склад. Пока защиты не было, это проходило незамеченным.

   Общая мысль: **три из четырёх аварий этого проекта были одинаковыми —
   молчаливыми.** Тихий выход, «код 2» без причины, и теперь отчёт «нет
   всего». Молчание стоит дороже ошибки: ошибку видно в логе, молчание
   выглядит как результат.

## Как продолжить работу в новом чате

Загрузить этот файл в новый чат с Claude и написать "продолжаем работу
над mail-automation" — Claude поймёт архитектуру, имена секретов (не
значения) и историю отладки без необходимости объяснять всё заново.

**Постоянное правило работы (действует в каждом чате):** после каждого
значимого изменения — вносить суть в этот README (в профильные секции и
запись в «Хронологии изменений») и сразу делать коммит с push в `main`.
README — единственный носитель контекста между чатами: если изменение
здесь не описано, оно считается потерянным.

## Диагностика логов: `tools/fetch_logs.py` (сентябрь 2026)

Автоматическое скачивание и разбор логов GitHub Actions — без браузера:

```
python3 tools/fetch_logs.py list          # последние запуски всех workflow
python3 tools/fetch_logs.py fetch <id>    # скачать лог запуска
python3 tools/fetch_logs.py analyze       # разбор всех логов: реальное время
                                          # исполнения, проекты, письма, ошибки
```

Токен берётся сам из связки ключей macOS (учётные данные git), вводить и
хранить его не нужно. `analyze` — первый инструмент для ответа на вопрос
"почему проект не уехал": сразу видно реальное (с задержкой) время
исполнения и результат диспетчера.
