## 1. ~~Критично — правила Firestore для `kpi_reports`~~ — ЗАКРЫТО (проверено 19.11)

Первоначальный вывод был неверным: я предположил, что в `ownerUid` пишется UID, а по коду пишется **email**. Фактическая цепочка:

- `RunProcessesPage.tsx:579` — если `owner_uid` пуст, подставляется `user?.email`;
- `kpi_sales.yml:10` — описание: «Email владельца, под которым сохранять отчёт»;
- `run_pipeline_kpi.py:193` — `owner_uid = os.environ.get("OWNER_UID") or notify_email`;
- `KpiPage.tsx:71` — `where('ownerUid', '==', user.email)`;
- `firestore.rules:105` — `resource.data.ownerUid == request.auth.token.email`.

Все пять мест согласованы на **email**, правило деплоится, отчёт доходит. Работает.

**Остаётся одна задокументированная особенность (не баг):** имена `ownerUid` / `owner_uid` врут — там email, а не UID. При доработке легко перепутать. Переименовать в `ownerEmail` при следующем рефакторинге, синхронно во всех пяти местах.

## 2. Безопасность — персональные данные клиентов в публичном репозитории

В git **закоммичены** файлы с ПДн клиентов (`git ls-files`):

| Файл | Содержимое |
|---|---|
| `mail-automation/scripts/clients_debt_ukhta.txt` | ФИО, ИП/ООО, адреса, **email** должников |
| `mail-automation/scripts/recipients_ukhta.txt` | список email получателей |
| `mail-automation/scripts/recipients_sety_ukhta.txt` | список email получателей |

`.gitignore` их игнорирует (строки 60–66), **но файлы были добавлены раньше и остаются отслеживаемыми** — исключения в `.gitignore` на уже отслеживаемые файлы не действуют. Репозиторий публичный (`github.com/BOBAH1988/ZOO_opt`), значит персональные данные видны всем.

По 152-ФЗ это обработка ПДн без надлежащей защиты. Кроме того, `check_secrets.py` тоже попал в перечень, хотя секретов не содержит — это ложное срабатывание.

**Что делать:**
1. `git rm --cached` для всех трёх файлов, коммит.
2. Загружать списки из GitHub Actions secrets / Firebase / отдельного приватного хранилища.
3. Помнить: история git сохраняет данные — при необходимости чистить историю (`git filter-repo`) и уведомлять затронутых лиц.

## 5. Логические ошибки в коде (остались после миграции)

### 5.1. `run_pipeline_kpi.py:188` — мёртвая переменная

```python
recipients = [notify_email]   # ruff F841: assigned but never used
```

Это остаток от старой логики рассылки: в комментарии рядом сказано «для хранения в Firestore», но в Firestore пишутся `html`/`plain`, а `recipients` не используется. Если на него опирались в старой версии — отчёты сейчас уходят не тем адресатам либо не уходят вовсе. Надо явно решить, нужен ли список получателей.

## 6. CI/CD и инфраструктура

### 6.1. `update_sales_report.yml` ставит только `requirements.txt`

`update_sales_report.yml:27` → `pip install -r mail-automation/requirements.txt` (там `openpyxl`, `xlrd`, `xls2xlsx`, `firebase-admin`). `update_sales_report.py` использует `openpyxl` — OK. Но `mail-automation/tests/` использует `pytest`, а `pyproject.toml` ссылается на папки `tests` и `tools` — они есть, проверено.

### 6.2. Локальный `firebase_admin` не установлен

Импорт `run_pipeline_kpi` падает локально с `ModuleNotFoundError: firebase_admin`, хотя в `requirements.txt` он есть. В CI ставится — там проблемы нет. Это значит, что локальная разработка после миграции не воспроизводит CI. Нужен `venv` + `pip install -r requirements.txt`.

### 6.3. `tsconfig.json` не включает `server/`

`"include": ["src", "vite.config.ts"]` — код Express (`server/index.js`) не типизируется и не проверяется линтером. При этом он содержит бизнес-логику безопасности (`ALLOWED_WORKFLOWS`, `REAL_SEND_UIDS`). Стоит добавить `checkJs` или перевести на TS.
