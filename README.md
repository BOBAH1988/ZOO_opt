# ЗооКонтроль — клиенты, отчёты, KPI, автоматизация

MVP-приложение для управления почтовыми автоматизациями. Скрипты автоматизации скопированы в папку `mail-automation/` этого репозитория, GitHub Actions workflow для их запуска лежат в `.github/workflows/`. Приложение размещается на GitHub Pages, использует Firebase Authentication и Firestore, а запуск GitHub Actions workflows выполняется через защищённый серверный API-посредник.

## 1. О приложении ZOO_opt

### Статус и реализованные доработки

- **Клиенты:** чтение/запись только по `ownerUid` текущего пользователя (`where('ownerUid','==',uid)`), запись реального UID из Firebase Auth, валидация структуры документов, безопасное преобразование `Timestamp/Date/string` в ISO, понятные ошибки, пропуск некорректных записей с предупреждением. В форме редактирования адрес приводится к формату «Город, улица дом» (старый вариант с точкой автоматически исправляется), форма выбирается из `ИП`/`ООО`, почта проверяется на корректный формат; у полей телефона и почты есть кнопки копирования, а в заголовке карточки — копирование всех данных клиента. Дополнительные поля: «Код клиента» (цифры или буквенно-цифровой код вида `06031`/`Б2902`, приводится к верхнему регистру), «Заказы» (произвольный текст), «Режим работы» (приводится к виду `10:00 - 21:00`), «Название» и «Грейд»; в карточке клиента «Создан»/«Обновлён» показываются в формате `13.11.26 11:05`, статус — символами `✓`/`✕`. Адрес хранится и одной строкой, и раздельно в полях «Город» и «Улица» (если «Адрес» не заполнен, он собирается из города и улицы). Почта необязательна — у клиентов из Excel её может не быть; при пустом значении в Firestore пишется `null`.
- **Импорт клиентов из Excel:** кнопка со стрелкой вверх в заголовке «База клиентов» открывает выбор файла `.xlsx/.xls/.csv`. Разбираются все листы книги: первая колонка каждой строки должна начинаться с кода клиента, за ним идёт ФИО/название, затем организационно-правовая форма (`ИП`/`ООО`/…), город и улица; полный адрес в скобках разбирается как в человекочитаемом виде («Республика Коми, г. Сосногорск, 6-й мкр., д. 28, магазин "Котопес"»), так и в выгрузке 1С. Регион, индекс и название магазина в адрес не попадают, название магазина записывается в «Название». Дубликаты внутри файла сворачиваются по коду (или по имени, если кода нет). Перед записью показывается диалог предпросмотра (первые 50 строк, счётчики «новых» и «обновляемых»): совпадения ищутся по коду клиента, затем по имени и адресу. У существующих клиентов обновляются название, адрес, город, улица, название и код; почта, телефон, заметки и остальные ручные поля сохраняются. Запись идёт пакетами `writeBatch` по 450 операций с таймаутом 30 секунд, идентификаторы новых документов — `crypto.randomUUID()`). См. `src/lib/salesImport.ts`, `src/pages/ClientsPage.tsx`.
- **Таблица клиентов:** колонка «№» с нумерацией всегда с 1 (не зависит от фильтра), фиксированная раскладка без горизонтального скролла, длинные значения обрезаются многоточием. В заголовке списка доступны сортировка по имени (по возрастанию/убыванию/по умолчанию) и режим ручного порядка со стрелками «выше/ниже»; активная кнопка сортировки подсвечивается голубым, выбранный порядок сохраняется в `localStorage` и применяется как значение по умолчанию, а высота строк при включении сортировки не меняется. См. `src/pages/ClientsPage.tsx`.
- **Маршрут:** клиенты сгруппированы по дням посещения. Рядом с днём недели показывается ближайшая дата в формате `Понедельник 16.11.26` (если дата прошла — следующая по календарю). В колонке «Адрес» показывается часть после запятой — улица и дом (например, «Ухта, Заводская 6» → «Заводская 6»). Строки таблицы компактные, всегда в одну строку: «Клиент» и «Адрес» обрезаются многоточием, отступы между столбцами минимальные, фиксированная раскладка не добавляет горизонтальный скролл, а при включении сортировки высота строк не увеличивается. Порядок клиентов можно менять стрелками «выше/ниже» (сохраняется в `localStorage`), есть сброс отметок посещения. План перед визитом оформлен как список «Планирование задач»: Enter добавляет новую строку, у каждой строки есть статус «Запланировано», «В процессе», «Выполнено» или «Удалить» (строки со статусом «Удалить» удаляются после сохранения), в просмотре показывается прогресс «Выполнено X из Y». См. `src/pages/RoutePage.tsx`.
- **Firestore Rules:** строгие правила владельца для `clients` и `runLogs`, запрет остального. Источник правил — `firestore.rules`; настройки Firebase CLI — `firebase.json`.
- **Запуск процессов:** клиент отправляет `Authorization: Bearer <Firebase ID token>`, параметры workflow редактируемы в UI (запоминаются в `localStorage`), перед запуском показывается полноэкранное подтверждение (Esc закрывает, прокрутка страницы блокируется) с явным предупреждением о реальной рассылке, журнал запросов пишется в `runLogs`. После запуска вместо кнопки показывается статус «Ок»/«Сбой»; нажатие на «Ок» скрывает статус и возвращает кнопку «Запустить» для повторного запуска, кнопки действия имеют одинаковую ширину. Кнопка `❓` рядом с заголовком открывает список всех сценариев запуска и всех скриптов с описаниями и кодами (скрипты лежат в папке `mail-automation/scripts/`). Списки проектов в настройках каждого сценария ограничены составом его workflow; сохранённые в `localStorage` лишние значения отбрасываются при загрузке. См. `src/pages/RunProcessesPage.tsx`, `src/api.ts`.
- **Сервер запуска:** `/server` содержит пример Express API, а `server/cloudflare` — Cloudflare Worker для бесплатного размещения с проверкой Firebase ID token, allowlist пользователя, валидацией workflow/inputs и серверным GitHub token. Требует развёртывания и настройки `VITE_API_BASE_URL`. См. `server/README.md` и `server/cloudflare/README.md`. **Безопасность по умолчанию — fail-closed:** пустой `ALLOWED_UIDS` запрещает запуск всем, пустой `REAL_SEND_UIDS` запрещает реальную рассылку всем.
- **Навигация:** внутренняя навигация через `Link`/роутер (HashRouter, base `/ZOO_opt/`), без обычных ссылок на внутренние маршруты вне роутера.
- **Регистрация/доступ:** вход, сброс пароля, опциональные ограничения регистрации (`VITE_DISABLE_SIGNUP`, `VITE_ALLOWED_EMAILS`, `VITE_ALLOWED_EMAIL_DOMAINS`, `VITE_REGISTRATION_INVITE_CODE`), попытка отправки письма подтверждения email после регистрации. Для внутренней системы рекомендуется отключить/ограничить регистрацию и управлять пользователями в Firebase. На странице входа не показывается футер.
- **Сессия и быстрый старт:** сохранённый пользователь читается из `localStorage` Firebase Auth, поэтому при обновлении страницы приложение открывается сразу, не дожидаясь сетевой проверки токена; реальное состояние из `onAuthStateChanged` применяется, когда SDK ответит. Если Firebase недоступен, через 8 секунд показывается экран входа с понятным сообщением (при явном offline — сразу), а не бесконечная загрузка. См. `src/context/AuthContext.tsx`.
- **Отчёты:** история запусков из `runLogs` (дата в две строки — дата и время, процесс, статус «Ок»/«Сбой»). Столбцы «Результат» и «Сообщение» скрыты; текст сообщения показывается во всплывающей подсказке при клике на статус. Статус «Ок» не означает завершение workflow.
- **PWA:** `public/sw.js` — чистый JS (версия кэша `v6`), кэш только статической оболочки, network-only для Firebase/API/авторизованных данных, внешние cross-origin запросы не перехватываются, ошибки `fetch` обрабатываются без необработанных промисов. `src/main.tsx` регистрирует SW только в production, а в dev снимает ранее зарегистрированный SW, чтобы не отдавались устаревшие файлы. В меню шапки есть кнопка «Установить»: она вызывает системный `beforeinstallprompt` (установка на телефон или ПК), а если приложение уже установлено, установка недоступна или произошла ошибка — открывает окно с краткой инструкцией под платформу (iOS, Android, компьютер, Firefox). Адаптация под устройства: `env(safe-area-inset-*)` для вырезов/домашнего индикатора iPhone, `touch-action: manipulation`, брейкпоинты до 480px, поля ввода 16px против зума iOS при фокусе.
- **CI/проверки:** `npm run lint` и `npm run test` = `tsc --noEmit`, `npm run build` = `tsc -b && vite build`; deploy workflow выполняет lint, загружает/валидирует Firebase-конфиг из секрета `ZOO` и собирает проект. Правила и индексы Firestore публикуются отдельно через Firebase CLI.

### Настройка Firestore в консоли Firebase (обязательно)

Даже если все `VITE_FIREBASE_*` заданы верно, ошибка `400 (Bad Request)` на потоке `google.firestore.v1.Firestore/Listen` означает, что **база данных Firestore не создана** в проекте Firebase или не настроены правила доступа.

### Шаги настройки

1. Откройте [Firebase Console](https://console.firebase.google.com/), выберите проект `zoo-opt`.
2. В боковом меню перейдите **Firestore Database** → **Create database**.
3. Выберите режим **Native mode** (рекомендуется), затем расположение БД (ближайшее к вам).
4. Нажмите **Enable** — создание может занять до 1 минуты.
5. В разделе **Firestore Database → Rules** замените правила на содержимое `firestore.rules` из этого репозитория и нажмите **Publish**:
   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       ... (см. firestore.rules)
     }
   }
   ```
6. В разделе **Firestore Database → Indexes** убедитесь, что индексы из `firestore.indexes.json` созданы (либо нажмите «Create index» при первом открытии страницы, которая требует составной индекс).
7. Скопируйте веб-конфигурацию: **Настройки проекта → Общие → Ваши приложения → Веб-приложение (</>)** → `firebaseConfig` и впишите значения в `.env` (`VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID` и т.д.).

### Почему возникает `400 Bad Request` на `Listen`

SDK Firebase пытается открыть веб-канал (WebChannel) для подписки на изменения в Firestore. Если база данных не создана, проект не имеет прав на Firestore или API-ключ не валиден, Google отвечает `400 (Bad Request)` и соединение рвётся. Это не ошибка кода приложения — необходимо завершить настройку в консоли Firebase.

### GitHub Secrets (deploy)

Для публикации через GitHub Actions создайте repository secret `ZOO` (Settings → Secrets and variables → Actions) со значениями веб-конфигурации Firebase из Firebase Console. Значение может быть строками `.env` (`ИМЯ=значение`, по одной на строку) или JSON-объектом с теми же ключами. Workflow записывает содержимое `ZOO` во временный `.env`, проверяет обязательные параметры входа (`VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`) и формат Firebase Web API key, затем собирает сайт.

Дополнительно (при необходимости) задайте секреты: `VITE_API_BASE_URL`, `VITE_DISABLE_SIGNUP`, `VITE_ALLOWED_EMAILS`, `VITE_ALLOWED_EMAIL_DOMAINS`, `VITE_REGISTRATION_INVITE_CODE`.

**Не храните реальные секреты/GitHub-токены в клиенте, `.env` в репозитории или README.**

### Firebase

- **Auth:** Email/Password. Включите провайдера в Firebase Console; настройте подтверждение email/сброс пароля и домены при необходимости.
- **Firestore:** коллекции `clients` (поля: `name`, `email?`, `phone?`, `company?`, `address?`, `city?`, `street?`, `day?`, `mode?` — режим работы в формате `10:00 - 21:00`, `manager?`, `notes?`, `active?`, `title?` — название магазина, `clientCode?` — цифры или буквенно-цифровой код, `orders?` — текст, `grade?` (Gold/Silver/Bronze), `createdAt`, `updatedAt`, `ownerUid`) и `runLogs`. Почта необязательна, пустые значения хранятся как `null`. Правила и индекс `runLogs` хранятся в репозитории; после изменения `firestore.rules` (новые поля `city`, `street`, `clientCode`, `orders`, необязательная почта) их нужно опубликовать заново, иначе импорт из Excel получит отказ по правам.
- Правило вида `allow create: if request.auth != null` для клиентов **не используется** — доступ ограничен владельцем и валидацией.
- После входа в Firebase CLI (`firebase login`) опубликуйте конфигурацию Firestore из корня репозитория: `firebase deploy --only firestore:rules,firestore:indexes --project zoo-opt`. Индекс `runLogs` поддерживает запрос отчётов по `requestedBy` с сортировкой по `createdAt`.

### Запуск GitHub Actions (сервер)

Клиент: `POST ${VITE_API_BASE_URL}/run` с JSON `{ workflowId, inputs }` и Firebase ID token. Сервер обязан:

- проверять токен и права пользователя;
- разрешать только workflow/параметры из серверного белого списка;
- валидировать входные данные и усиливать ограничения для реальных рассылок (`test_mode`, allowlist/роль, журнал);
- хранить GitHub token/credentials только на сервере.

Ответы об ошибках содержат машинный код причины в поле `code`, чтобы клиент не показывал внутренний текст GitHub: `github_timeout` (504), `github_auth_failed`, `github_forbidden`, `github_not_found` (502), а также `missing_token` (401), `invalid_token` (401), `unverified_email` (403), `uid_not_allowed` (403). Клиент переводит их в русские тексты через `ERROR_CODE_MAP` в `src/api.ts`.

Пример реализации: `server/README.md`. Без настроенного API запуск не выполняется.
Бесплатный вариант размещения — Cloudflare Workers; пошаговая настройка находится в `server/cloudflare/README.md`. Для работы нужны GitHub token в секрете Worker и URL Worker в GitHub Secret `VITE_API_BASE_URL`.

## 2. Автоматизация почты (mail-automation)

Все скрипты автоматизации скопированы в папку `mail-automation/` этого репозитория. GitHub Actions workflow для их запуска лежат в `.github/workflows/`. Система предназначена для автоматизации рутины в почте и закупках: рассылка прайсов, пересылка заказов и счетов, ответы по дебиторке — идут сами, по расписанию или по ручному запуску через PWA-приложение.

### Польза в трёх вещах

- **Экономит время.** Регулярные действия — рассылка прайсов, пересылка заказов и счетов, ответы по дебиторке — идут сами, по расписанию.
- **Поднимает качество.** Одно и то же письмо уходит всем адресатам и одинаково: проценты, адреса, вложения не зависят от того, кто и когда нажал кнопку.
- **Убирает случайные ошибки.** Проверки и защиты от повторов не дают разослать прайс дважды, отправить счёт не тому клиенту или выпустить отчёт, посчитанный по неразобранному файлу.

## 3. Проект рекомендации к заказу (project residues / проект 13)

Система рекомендаций к заказу: находит среди товаров, которые **реально продавались**, те, которых **нет** на текущем остатке. Именно они выпадают из продаж — менеджер по закупу сейчас ищет их вручную в Excel, из-за чего часть товаров теряется.

Это единственный проект репозитория, у которого собственная папка с кодом (`mail-automation/project residues/`) и собственный workflow: он не делит библиотеку с почтовыми сценариями, а запускается из `scripts/run_pipeline_residues.py`, который забирает прайс остатка из письма и присылает отчёт обратно на почту.

### Зачем эта система

Показывает, **чего не хватает на складе Ухты**: какие позиции продавались, но сейчас не поставляются. Всё считается из двух файлов, оба приходят письмом.

Менеджеру нужно одно: распечатать лист «Нет на остатке» и отправить заявку.

### Как это работает

Три файла, один результат:

| Файл                                               | Что это                                        | Откуда                      |
| ------------------------------------------------------ | ---------------------------------------------------- | --------------------------------- |
| `Весь ассортимент за 3 мес.xlsx` | продажи за 3 месяца в штуках   | 1С, лежит в проекте |
| `Полный прайс.xlsx`                       | весь ассортимент поставщика | лежит в проекте      |
| `прайс Ухта.xlsx`                           | что Ухта поставляет сейчас    | приходит письмом   |

```
продажи за 3 мес  →  что продавалось  →  сверка с прайсом Ухты  →  заказ
                                                   (чего нет = заказываем)
```

Отчёт состоит из трёх листов:

| Лист                                            | Что внутри                                                                                                                                                                                                  |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Сводка**                              | ключевые числа и топ-10 позиций по штукам                                                                                                                                            |
| **Нет на остатке**                | сам заказ: одна таблица с фильтром по каждой колонке                                                                                                                      |
| **Нет на остатке 2 недели** | позиции, которых нет и сейчас, и в предыдущем файле остатка — двойное отсутствие говорит о явной проблеме с закупкой |

### Где что лежит

```
mail-automation/project residues/
├── Весь ассортимент за 3 мес.xlsx   продажи из 1С
├── Полный прайс.xlsx                 полный ассортимент
├── прайс Ухта.xlsx                   остатки (обновляется письмом)
├── data/order.yaml                   настройки (порог, сходство)
├── output/                           готовые отчёты
└── residues/                         код
```

Единственная настройка — `data/order.yaml`:

* `min_period_sales` — порог отсечения в штуках за 3 месяца;
* `min_similarity` — насколько похожими должны быть названия при перевыданных артикулах (0.8).

### Главное правило: в отчёте нет денег

В отчёте о продажах **нет колонок с суммами** — только штуки. Выводить рубли можно было бы умножением на оптовую цену из прайса, но тогда на вопрос «откуда сумма» ответа не было бы: продажи в 1С по рознице, а цена в прайсе оптовая.

Поэтому в отчёте только штуки. Упаковки не пересчитываются: сколько штук в упаковке, в данных написать негде, а спросить — значит ждать ответа на каждой партии.

### Что значат колонки в таблице заказа

| Колонка                    | Что в ней                                                        |
| --------------------------------- | ----------------------------------------------------------------------- |
| Название                  | как называется в полном прайсе                |
| Артикул                    | как называется поставщику                        |
| Раздел                      | для фильтра по группам товаров                |
| Продано шт за 3 мес | продажи за период — факт из 1С                   |
| шт за сент 26             | продажи за последний месяц — факт из 1С  |
| Рек. зак. в шт.          | среднее за 3 месяца: сколько заказывать |

**Как считается «Рек. зак. в шт.»** — это среднее число штук за 3 месяца, то есть месячная потребность:

```
продажи за 3 месяца ÷ 3
```

Минимум — одна штука: товар, который продался хотя бы раз, не может показать ноль, иначе менеджер увидит прочерк на продающемся товаре.

Все числа в столбце — **числа**, а не текст: сортировка и числовой фильтр по нему работают.

### Что система делает с товаром сама

1. **Отсекает непродающееся.** Позиция, которая не продалась за 3 месяца, в заказ не идёт. Отсутствие товара на остатке само по себе не доказывает спроса на него.
2. **Отсекает позиции без артикула.** Без артикула позицию невозможно ни найти у поставщика, ни сверить с остатком после поставки — нечего вписать в накладной. Строки 1С с пустым артикулом вдобавок вызывают подозрение: таких 31 из 4 257, и у самых крупных все три месяца круглые числа (600/300/200), а кассовые продажи таких значений не дают.
3. **Разводит акции и обычный товар.** 1С считает акцию отдельной единицей учёта: по базе 0702 в отчёте две строки — обычная на 929 шт и акционная `[0702АКЦИЯ]` на 56 шт. Акция берёт продажи только своей строки, а такая же позиция без акции — только своей.
4. **Разводит цвета.** Поводки идут как `[021621]`, `[021621оранж]` и `[021621син]` — названия одинаковые, различие только в артикуле.
5. **Сверяет вес и объём.** «Эдалт Сенсибл Мини ягн/томат 10кг» и такой же «3кг» — разные упаковки, и одна не подтверждается продажами другой.
6. **Ищет товар по названию**, если артикул перевыдали. Сходство названий должно быть не меньше порога из `order.yaml` (по умолчанию 0.8).

### Настройка: что попадает в заказ

Всё в `data/order.yaml`, менять можно без программиста:

```yaml
min_period_sales: 0      # порог отсечения в штуках за период
min_similarity: 0.8      # насколько похожими должны быть названия
```

**`min_period_sales: 0`** — ничего не отсекать. Поставьте 500 — в заказ попадут только позиции, продавшие 500+ штук за квартал.

**`min_similarity: 0.8`** — строже обычного. Поставьте 0.6 — больше угаданных пар, но и больше сомнительных совпадений.

### Полезные команды

```bash
python3 -m residues --order                # собрать отчёт
python3 -m residues --order --to-downloads # и положить копию в «Загрузки»
python3 -m pytest -q                       # проверить, что всё работает
```

Автозапуск: система сама забирает письмо с прайсом Ухты **по понедельникам в 10:00–11:00 МСК**, собирает отчёт и присылает его на почту.

### Если что-то пошло не так

**Позиций в заказе слишком много или слишком мало.** Проверьте период в отчёте о продажах: он должен быть последними 3 месяцами.

**Товар есть в заказе, но на самом деле он есть на складе.** Проверьте, нет ли его в `прайс Ухта.xlsx` под другим названием.

**Позиция не нашлась в продажах.** Скорее всего, артикул перевыдали. Поищите название вручную: `python3 -m residues` покажет числа.

### Итого: что делать каждую неделю

1. Открыть письмо с прайсом Ухты.
2. Система в понедельник соберёт отчёт и пришлёт его на почту.
3. Открыть лист «Нет на остатке», отсортировать по «Продано шт за 3 мес».
4. Заказать позиции сверху вниз, пока хватает места в заказе.
5. Отдельно проверить лист «Нет на остатке 2 недели» — позиции там отсутствуют уже две недели подряд, это явная проблема с закупкой, их нужно брать в первую очередь.

### Зависимости

`openpyxl`, `xlrd` (для `.xls`), `PyYAML` (для файла настроек `data/order.yaml`). Все три уже числятся в `requirements.txt` репозитория.

### Защита от повторной отправки (дубли)

Чтобы не слать один и тот же отчёт каждую неделю, проект не может погасить письмо с прайсом (оно приходит уже прочитанным), поэтому повтор отсекается по дате: маркер на диске и проверка папки «Отправленные» через IMAP.

**Ручной запуск (workflow_dispatch)** — защита от дублей отключена: проект отрабатывает всегда, даже если сегодня уже уходил отчёт. Это нужно, чтобы перезапустить проект после сбоя или при отсутствии письма от оператора.

**Авторассылка (schedule)** — защита включена. Если отчёт сегодня уже уходил, срабатывает защита: повтор не отправляется, а на `NOTIFY_EMAIL` уходит уведомление с текстом:

    Это рассылка сегодня уже выполнена. Повтор не отправлен.
